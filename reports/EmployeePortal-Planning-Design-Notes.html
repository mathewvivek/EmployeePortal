Design Notes

A desktop-first HR workspace for employee records, annual base salaries, compensation insights and traceable salary reviews.

21 / 29Reporting features completed

Purpose

Replace scattered compensation spreadsheets with a searchable directory, validated salary updates, immutable application-level history and currency-specific summaries. Give HR useful review indicators without automatically deciding that a salary is wrong or unfair.

Audience and Permissions

The current persona is one seeded HR superadmin. This user can view dashboards, create employees, update salaries with confirmation, read salary history and investigate data-quality findings. There is no employee self-service, public registration or separate read-only HR role.

Architecture Design

BoundaryResponsibilities

Backend/JSON API under /api/v1. Controllers handle auth, parameters and HTTP responses; models enforce record rules; services own updates and reporting.

DatabaseSeven primary application tables. PostgreSQL performs aggregates and cohort calculations, enforces integrity and supports transactional locks.

Design Rationale

  • Keep the browser focused on interaction, not duplicating backend financial or review rules.
  • Use service objects for atomic writes and complex reads without introducing a separate service or distributed transaction.
  • Separate static frontend and API deployments; retain one repository and independent CI checks for each.
  • Keep the public Rails root separate from the HR application. It reports liveness, not database readiness, and contains no endpoint documentation.

Data Model Decisions

TablePurpose and Important Relationships
employeesCurrent directory and annual compensation. Unique string business employee_id; numeric primary id for API lookups and foreign keys.
salary_changesOld/new amounts, currencies, effective dates and change timestamp; belongs to an employee.
usersHR credentials and activity status. Separate from employee payroll records; no user-to-employee link is implemented.
sessionsToken digest and expiry; belongs to an HR user.
salary_data_quality_scansRun timing, requesting user and summary counters.
salary_data_anomaliesFingerprint, rule, severity and JSONB evidence; employee and latest detecting scan; optional latest reviewer.
salary_data_anomaly_reviewsDecision, notes, author and time; belongs to a finding and HR user.

Identity, Precision and Integrity

  • Seven bigint primary keys, eight foreign keys, 19 secondary indexes and nine CHECK constraints. Four secondary indexes are unique.
  • employees.employee_id is a business string, while salary/finding employee_id references employees.id. Do not interchange these identifiers.
  • Salary columns use numeric(18,2). API amounts are fixed two-decimal strings; server calculations round only reported values.
  • Database constraints enforce supported currencies, employee status, nonnegative pay, review statuses and superadmin role. Required strings also receive Rails nonblank validation.
  • Country, department and designation are strings, not normalized reference tables. JSONB evidence is required, but its shape is enforced by application construction rather than a SQL JSON schema.

History and Deletion Policy

Salary changes and review events are read-only once persisted through Rails. This is not a database-level immutable ledger: direct SQL can bypass the guard. Foreign keys do not cascade-delete audit records. Model associations restrict deleting employees/findings with history. Salary history does not currently store the editing HR user's ID.

API Design Notes

JSON resources are grouped under /api/v1. Protected operations require an active HR superadmin bearer session and use Cache-Control: no-store. This internal document is not served on the public backend status page.

OperationContract / Purpose

GET / DELETE /session		Login accepts a session email/password object. Return/verify the user and expiry; revoke the current session on logout.

POST /employees		Paginated search/filter/sort; validated employee creation. Collection reads return data plus page/count metadata.
GET /employees/:idRead identity and compensation using numeric database ID.
GET /employees/:id/salary
PATCH / PUT same path		Read or update base_salary, currency and effective_date. Updates require confirmed: true in the salary object.
GET /employees/:id/salary_historyRead old/new compensation and change timestamps; no history-edit endpoint.
GET /compensation_insights
GET /salary_analysis		Currency-separated summaries and paginated reports selected by report parameter.
POST /salary_data_quality_scansRun synchronous manual checks across the database; return completed scan counters.
GET /salary_data_anomalies
GET / PATCH / PUT /salary_data_anomalies/:id		Filtered queue, evidence and paginated review history; append HR decisions without writing salaries.

All paths in the table are relative to /api/v1. Nested salary routes use employee_id as the route parameter name, but its value is still the numeric employees.id.

Query and Error Rules

Country, department and status combine; directory search uses case-insensitive name/business-ID matching. Directory and analysis pagination defaults to page 1 / 25 rows, capped at 100; positive integers are required. Stable ties use employee ID or the report's group names.

Typical status codes: 200 read/update; 201 login/create/scan; 204 logout; 400 malformed required object; 401 invalid session; 403 wrong role; 404 unknown record; 409 stale finding review; 422 validation; 429 login limit.

Salary Transaction Boundary

SalaryUpdater locks the employee, captures existing values, validates the requested values, saves only when changed, then writes history within the same transaction. Failed validation/history insertion rolls back the update. Identical values create no change row. A future effective date is stored immediately; there is no deferred activation scheduler.

Currency and Salary-Band Policy

Supported currencies: INR, USD, GBP, EUR and JPY. Band boundaries are INR 500,000 / 1,000,000 / 2,000,000; USD, GBP and EUR 50,000 / 100,000 / 150,000; JPY 3,000,000 / 6,000,000 / 9,000,000. Zero-count bands remain visible and the last band is open-ended.

Scope Before Pagination

Insight filters apply to every statistic. Salary-analysis filters define the entire comparison population before paging employee/group results. Default scopes include active and inactive employees; choose active explicitly when estimating active-staff base pay.

Query Design

CompensationInsights uses PostgreSQL grouping sets and filtered band counts rather than loading every employee into Ruby. SalaryAnalysis computes cohort statistics in SQL and loads only a requested page. Rankings in the UI use the returned currency-specific aggregates.

Interpretation: currency-specific reports deliberately avoid fabricated FX conversion. Current salary plus history is not enough to reconstruct certified year-over-year payroll expenditure without additional rules for employee populations and timing.

Employee PortalSalary Data-Quality Design

Checks and Review Lifecycle

CheckImplemented Trigger
Active zero payActive employee with base_salary = 0. Inactive zero pay is not flagged by this rule.
Extreme peer ratioPositive salary at least 10 x, or at most 0.1 x, positive median; same country/role/currency; minimum five employees.
Annual/monthly patternLatest same-currency change near 12 x or 1/12 x a positive old salary, within 2% tolerance.
Large salary changeLatest same-currency change increases at least fivefold or falls at least 80%; annual/monthly pattern takes precedence.
Same amount, new currencyCurrency switched while an identical positive numeric amount remained; information flag, not assumed conversion error.
Distant future dateCurrent effective date more than 365 days after scan date; shorter future dates remain valid.
History mismatchCurrent amount/currency/effective date differs from latest history, ordered by changed_at then ID descending.
Blank detailsBlank business ID, name, department, country or designation, potentially after an import bypassing Rails validation.

Scan Design

Manual synchronous scan, 500 employees per batch, one grouped peer-statistics query and a lateral latest-history lookup. A PostgreSQL transaction advisory lock serializes full scans. Scan and findings roll back on failure. Fingerprints reuse unchanged evidence and preserve prior decisions.

Decision State Is Separate From Finding Activity

Pending, Investigating, Confirmed error and Legitimate are HR decisions. Active/Cleared is detection state. Confirmed error and Legitimate require notes, capped at 2,000 characters. Every saved decision appends reviewer/time history and updates the finding's latest decision.

Source changes or cleared findings reject review with 409 after locked revalidation. A rescan clears superseded/no-longer-detected evidence without deleting its reviews. Changed evidence creates a new Pending finding. Corrections use the normal confirmed salary-update flow; scans never edit salaries.

Review Queue and Limits

Default UI is active Pending findings. Currency/employee/decision filters, pagination and Include cleared are available. Filters narrow the queue, not scan baselines; peers include active and inactive employees. Counters cover all employees and results are as of the last check, not continuous monitoring.

Employee PortalSecurity and Privacy Design

Access and Protection Notes

Implemented ControlDesign / Limit
AuthenticationBcrypt password hashes, active-user checks and opaque random bearer tokens. PostgreSQL stores SHA-256 token digests, not raw tokens.
Session lifecycleEight-hour sessions; logout revokes the current token; password/activity changes revoke user sessions. Browser verifies a saved session before showing protected views.
Browser storagePer-tab sessionStorage, with in-memory fallback. This limits persistence but is still accessible to same-origin JavaScript; it is not an HttpOnly cookie.
AuthorizationOnly the superadmin role is supported; server-side checks protect employee, insight and review routes. Hiding a button or route list is not authorization.
Abuse resistanceLogin allows 10 attempts per IP per three minutes through a process-local MemoryStore. This is not a shared global limit across multiple Rails processes.
Browser origin policyRestricted frontend origin for /api/* and explicit methods including OPTIONS. CORS permits a browser origin; it does not authenticate an API caller.
Public backend pageApplication liveness, time and portal link only; no route list/version/base path. CSP restricts scripts to self and prevents framing; no employee queries for status.
Secret handlingBackend environment for Rails key, DB connection and HR provisioning password; parameter-log filtering. No credentials in VITE_ values, screenshots or PDFs.

Proposed Production Hardening

  • Review frontend CSP and dependencies, and avoid untrusted scripts because browser bearer storage remains vulnerable to same-origin script compromise.
  • Use a shared login-rate-limit store before scaling to multiple processes; assess MFA or managed identity before adding broader access.
  • Rotate any exposed secrets; apply least-privilege database access; define backup/restore, retention and salary-data incident procedures.
  • Consider database-level audit protections and adding the salary-changing actor if stronger traceability is required.

No claim is made that an independent penetration test, comprehensive security audit or production readiness certification has been completed.

Performance Decisions Already Implemented

  • Server pagination with a 100-row API cap and indexed salary/filter/foreign-key paths; 300 ms debounced directory search.
  • SQL aggregation for insights and peers; latest history loaded in batched queries, not per employee.
  • Explicit manual scans and disabled duplicate actions in the UI. Scans still run inside a web request and may become expensive on larger data.

Proposed Acceptance Before a Production Release

  1. Run the full test/build/security pipeline on the exact release commit and add a real staging login-to-salary-change-to-history flow.
  2. Benchmark warm and cold start behavior, p50/p95 response times, concurrent browsing/writes and scans on deployment-sized hardware. Agree response-time targets from those results.
  3. Profile indexed queries and ILIKE search before adding indexes or caching. Introduce a background scan with progress only if request timeouts/resource pressure warrant it.
  4. Test failed migrations, backups/restores, network interruption and stale concurrent salary editing; verify accessibility and long-content layout.

Precision risk to address: backend amounts retain decimals as strings, but the UI money formatter currently converts them to JavaScript Number. Very large values near the database's numeric limit may lose cents in display; add a safe display-range rule or decimal-aware formatting before using such values.

Proposed Release Sequence

  1. Review and commit the intended changes; run CI and record the exact release hash. Review backups before applying schema changes.
  2. Apply backward-compatible primary migrations, including 20261013000004 for anomaly reviews, before code needs the new tables. Verify migration status in the hosted database.
  3. Deploy Rails and build/deploy the frontend with the matching API contract and correct API base URL. Verify CORS preflights and HTTPS access.
  4. Provision the single HR account if absent; seed synthetic employees only for an approved demo. Existing passwords are preserved unless explicit rotation is enabled.
  5. Smoke-test sign-in, directory, confirmed salary/history, insights, anomaly scans/reviews, expiry/sign-out and public health. Then remove one-time seed/rotation flags.
  6. Monitor failures and latency; keep a known-good application release and compatible schema. A database rollback is not assumed safe after salary/audit writes.

Proposed Delivery Order, Not a Committed Schedule

Risk Register and Open Choices

  • Concurrent edits: row locks preserve atomic history, but there is no optimistic version check for an old browser salary form. Add stale-edit detection before multi-user expansion.
  • Audit strength: history lacks the salary-changing actor and immutability is application-level. Decide whether stronger attribution/database controls are required.
  • Scale: scans are synchronous and login limits process-local. Revisit background jobs, query plans and a shared limit store as workload grows.
  • Business semantics: agree active-only defaults, reference-value governance, effective-date scheduling and anomaly thresholds before interpreting reports as payroll or policy.
