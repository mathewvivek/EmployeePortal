Scope and Identity

  • Every application table has a sequence-generated bigint id primary key and required created_at / updated_at timestamps.
  • employees.employee_id is a string business ID. Other tables' numeric employee_id foreign keys reference employees.id, not that business ID.
  • Framework bookkeeping tables schema_migrations and ar_internal_metadata are excluded from the seven-table count. Rails model Compensation is not a persisted table.
  • This is the primary application schema. Production configuration also names cache, queue and cable databases; their schemas are not covered here.

Database Guarantees and Operating Notes

Enforced by PostgreSQL

  • Seven primary keys, eight foreign keys and 9 CHECK constraints. There are 19 secondary indexes, four unique, in addition to the seven primary-key indexes.
  • Unique secondary indexes protect employee business IDs, user emails, bearer token digests and anomaly fingerprints.
  • Annual salary amounts use exact numeric(18,2): up to 16 integer digits and two decimal digits. Supported currencies are INR, USD, GBP, EUR and JPY. Monetary aggregates never combine currencies.
  • Dates use PostgreSQL date. Timestamps use timestamp(6) without time zone; Rails manages application time interpretation. JSONB evidence defaults to an empty object and is required, but has no database-level JSON shape constraint.
  • All eight foreign keys have default NO ACTION behavior for deletes and updates: no database ON DELETE CASCADE is declared.

Enforced by Rails, Not Database Triggers

  • Required strings must be nonblank; NULL constraints alone do not reject whitespace. Email normalization and format checks run in Rails.
  • Salary changes require explicit confirmation. Employee updates and their history rows are written atomically while locking the employee.
  • Salary history and anomaly review records are read-only once persisted through Active Record. Direct SQL can bypass this application safeguard.
  • Review notes are required for Confirmed error and Legitimate, and are limited to 2,000 characters. Those conditional requirements are not SQL constraints.
  • Deleting an employee with history/findings, or a finding with reviews, is restricted by model associations. User deletion destroys sessions through Rails; audit foreign keys can still prevent deleting that user.

Data-Quality Lifecycle

A scan writes summary counters and fingerprints matching findings. Unchanged reruns retain the existing finding and HR decision. Changed evidence creates a new Pending finding; cleared evidence stays stored with active=false and cleared_at. HR decisions append review events, and the finding caches the latest reviewer, notes and status. Scans never automatically alter salary.
